Qué debe verse Como mínimo: git version 2.47.1.windows.1, Docker version 29.5.3-rd, kubectl v1.34.6 y minikube version: v1.38.1.
Explicación Inventario de las herramientas del entorno de trabajo. 21kubectl logs

E8 · OperaciónSección logs de 05-pruebas.ps1
Comando
kubectl --context minikube logs -n micro-calc -l app.kubernetes.io/name=micro-calc --tail=20 --prefix
Explicación Logs agregados de todos los Pods mediante el selector de etiquetas -l app.kubernetes.io/name=micro-calc, sin nombrar ningún Pod concreto. Se confirma Spring Boot 4.1.0 sobre Java 21.0.12.1 y, crucialmente, PID 1: gracias al ENTRYPOINT en exec form, el proceso java es PID 1 y recibe SIGTERM directamente, lo que permite un apagado ordenado cuando Kubernetes retira el Pod. Con shell form, /bin/sh sería PID 1 y se tragaría la señal.

22Borrado de un Pod y su recreación

E8 · OperaciónSección resiliencia de 05-pruebas.ps1
Comando
kubectl --context minikube delete pod <nombre> -n micro-calc
kubectl --context minikube get pods -n micro-calc -o wide
Hay que capturar rápido La fase intermedia (Terminating + ContainerCreating) dura unos pocos segundos. El script imprime las tres fases seguidas para que quepan en una sola captura.
Explicación Prueba de autorreparación. Quien recrea el Pod no es el Deployment sino el ReplicaSet: su bucle de reconciliación detecta que hay 1 Pod donde debería haber 2 y crea uno nuevo en segundos. La columna AGE delata cuál es el Pod nuevo. El servicio nunca se interrumpió: la otra réplica siguió atendiendo peticiones durante todo el incidente.

Detalle observado: el túnel de port-forward sí se cortó, porque kubectl port-forward svc/… no balancea — elige un Pod concreto y mantiene el túnel contra él. Es una limitación de la herramienta de depuración, no un fallo del Service.

Explicación HPA operativo con métricas reales. Que aparezca 1%/70% y no <unknown>/70% demuestra dos requisitos cumplidos:

25Endurecimiento de la imagen

E4 · Imagen localPaso 8 de 01-build-local.ps1
Comando
docker exec micro-calc id
docker exec micro-calc cat /proc/1/cmdline
docker run --rm --memory=512m --entrypoint java gthen95/micro-calc:1.0.0 -XX:MaxRAMPercentage=75 -XX:+PrintFlagsFinal -version
Qué debe verse 
a) uid=10001(spring) gid=10001(spring) groups=10001(spring)
b) java -XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError -jar /app/app.jar
c) size_t MaxHeapSize = 402653184
   [OK] Heap maximo = 384 MiB = 75 % de 512 MiB. CORRECTO.
Explicación Verificación empírica de tres decisiones de diseño:
  • el proceso corre como usuario no privilegiado (UID 10001), requisito de runAsNonRoot: true en el securityContext;
  • java es PID 1 gracias al ENTRYPOINT en exec form;
  • -XX:MaxRAMPercentage=75 respeta el límite del contenedor: con --memory=512m la JVM se asigna 384 MiB de heap.
Sin ese último flag, la JVM calcularía el heap sobre los 63 GB del anfitrión, superaría el limit de 512 Mi y Kubernetes mataría el Pod con OOMKilled. Es el error clásico de ejecutar Java en contenedores.

A · El fallo de TLS en Maven

[FATAL] Non-resolvable parent POM ... spring-boot-starter-parent:pom:4.1.0 (absent)
Could not transfer artifact ... from/to central (https://repo.maven.apache.org/maven2):
(certificate_unknown) PKIX path building failed: unable to find valid certification
path to requested target

B · Los Pods en ImagePullBackOff

Failed to pull image "gthen95/micro-calc:1.0.0":
Get "https://auth.docker.io/token?...": tls: failed to verify certificate:
x509: certificate signed by unknown authority
Diagnóstico y solución La red corporativa usa un FortiGate con inspección TLS selectiva: intercepta repo.maven.apache.org, auth.docker.io, github.com y ghcr.io, pero no registry-1.docker.io, mcr.microsoft.com, registry.k8s.io ni gcr.io.

Windows y la distro WSL2 de Rancher Desktop sí confían en esa CA (TI la instaló en LocalMachine\Root), pero cada contenedor trae su propio almacén de certificados: ni el cacerts de la JVM en la etapa build, ni el nodo Debian de Minikube, la tenían.

Solución: inyectar la CA corporativa en ambos sitios, sin desactivar la validación TLS y sin publicar los certificados en el fork público.
Lección de método El síntoma de (A) era idéntico al que se anticipaba como «Nexus corporativo sin sincronizar», cuyo plan B era degradar a Spring Boot 3.5.x. Leer el mensaje completo —la causa real estaba varias líneas más abajo— y comprobar que repo.maven.apache.org respondía HTTP 200 desde Windows evitó una degradación innecesaria del proyecto. Se mantuvo Spring Boot 4.1.0 sin tocar el pom.xml.

«El artefacto no se pudo resolver» y «el artefacto no existe» son cosas distintas.
